# 낙상 이벤트 보관과 재전송

`FD_KWS_GPS`만 이벤트를 NVS의 `fall_outbox`에 저장한 후 전송한다. 서버가 HTTP 2xx로 수락한 경우에만 해당 저장 항목을 지운다. 연결 또는 HTTPS 요청이 실패하면 이벤트 ID·상태 보고 생성 시각·순번을 그대로 유지하고 1초부터 최대 30초까지 간격을 늘려 재시도한다. `deviceTimeMs`는 safe/danger 보고를 큐에 넣은 시점의 uptime이며 최초 낙상 후보의 절대 시각이 아니다. 재부팅하면 NVS 항목을 읽어 전송을 재개한다. NVS 초기화 실패 시 저장 공간을 자동으로 지우지 않는다.

영구 보관 용량은 32개이며 RAM 대기열도 32개다. 감지 호출은 RAM에만 넣고 즉시 반환한다. 별도 저장 작업이 NVS 기록을 재시도하고 전송 작업이 HTTPS 재전송을 담당한다. 저장·전송 실패 때문에 새 낙상 판정을 보류하지 않으며 기존 판정 후 쿨다운은 유지한다. 두 보관소 모두 가득 차면 새 이벤트 종류와 관계없이 순번이 가장 작은 오래된 이벤트를 교체한다. 새 안전 이벤트도 오래된 위험 이벤트를 교체할 수 있다. 교체는 용량 초과 시 이전 이벤트의 소실을 허용하고 최신 이벤트 보관을 우선하는 정책이다. NVS 기록 실패 시 기존 영구 이벤트를 유지하고 RAM 이벤트를 다시 저장한다. RAM에만 있는 이벤트는 전원 차단 시 복구할 수 없다. 전송은 위험 이벤트부터, 같은 등급에서는 순번 순으로 처리한다.

ESP32는 생성한 128비트 임의 ID를 `eventId`로 전송한다. 서버는 `(deviceId, eventId)`로 Firestore 문서 ID를 만들고 트랜잭션으로 전역 이벤트·보호자 사본·기기 상태를 한 번 기록한다. 동시 요청이나 성공 응답 유실 후 재전송은 기존 이벤트를 반환하고 푸시 전송을 반복하지 않는다. 같은 ID로 내용이 달라지면 409를 반환한다. 이미 기록된 이벤트는 기기 연결이 나중에 변경되어도 인증 토큰이 유효하면 중복 요청으로 수락한다.

영구 순번 `eventSequence`로 이전 안전 이벤트가 늦게 도착해 더 최신 위험 상태를 덮어쓰는 것을 막는다. 순번은 이벤트 삭제와 재부팅 후에도 유지된다. NVS를 수동으로 지우거나 보드를 교체해 순번을 초기화할 때는 관리자가 해당 기기의 `latestEventSequence`도 초기화해야 한다. 기존 기록은 삭제할 필요가 없다.

기기 ID를 교체할 때는 먼저 보관 이벤트의 전송을 끝내야 한다. 현재 보관 레코드는 전송 시 펌웨어에 설정된 기기 ID를 사용한다.

## FD_KWS와 Fall_detection의 현재 전송 방식

현재 `FD_KWS`는 Fin 버전으로 복원됐으며, `Fall_detection`도 2026-10-13에
그 낙상·전송 부분으로 맞췄다. 두 프로젝트 모두 이 문서의 영구 보관 방식을 포함하지 않는다.
`main/fall_alert_sender.cc`는 RAM 큐 4개와 최대 3회 HTTP 전송을 사용한다.
Wi-Fi 재접속은 별도로 1~30초 backoff를 적용하지만 이벤트 자체는 세 번 실패하면
재보관하지 않는다. RAM 이벤트는 재부팅·전원 차단 후 복구되지 않는다.
요청에 `eventId`/`eventSequence`가 없어 서버의 ID 기반 중복 방지와 순번 보호도
적용되지 않는다. 같은 기기 요청의 성공 응답 유실 후 재전송은 중복 기록·푸시를
일으킬 수 있다. 따라서 보고서에서 FD_KWS 또는 Fall_detection의 기능으로 NVS 보관·재부팅 복구·
중복 방지 완료를 기술하면 안 된다. [FD_KWS 설명](../FD_KWS/README.md)을 참조한다.

## 적용 순서

1. Care_app에서 수정된 `reportFall` 서버 함수를 배포한다.
2. 영구 보관 방식을 적용하려면 FD_KWS_GPS를 빌드해 ESP32에 업로드한다. 일반 `flash`는 NVS를 유지하지만 `erase-flash`는 보관 이벤트와 순번도 삭제한다.
3. Wi-Fi를 끊고 이벤트를 발생시킨 후 재연결해 기록이 전달되는지, 저장 후 재부팅해 복구되는지 확인한다.

```powershell
cd Care_app
firebase deploy --only functions:reportFall
```

구형 펌웨어처럼 eventId 없는 요청도 받아 전환 중 호환성을 유지한다. 단, 그런 요청에는 중복 방지가 적용되지 않는다. 401·409 등 설정 오류도 이벤트를 버리지 않고 보관하므로 토큰·연결 설정 문제는 별도로 해결해야 한다.

## 검증과 보장 범위

현재 정지 억제는 모든 펌웨어에서 제거됐다. 2026-10-13 코드 변경 후의 빌드와
검증 결과는 [변경·검증 기록](../FIRMWARE_ALIGNMENT.md)을 참조한다. 아래의
2026-10-08 빌드·배포 결과는 당시 기록이며 현재 단독 펌웨어의 영구 보관을 뜻하지 않는다.

당시 로컬 검증 기록: Node 서버 테스트 24개 통과, C++ 보관소 테스트 통과. 당시 IDF 5.5.4에서 통합 펌웨어(당시 이름 FD_KWS, 현재 보존 위치 FD_KWS_GPS; 수집 OFF, TEST OFF)와 Fall_detection(수집 OFF, TEST ON)의 빌드·링크·파티션 크기 검사가 통과했다. 로그는 `FD_KWS_GPS/delivery_build.log`와 `Fall_detection/delivery_build.log`에 있다. 복원된 현재 FD_KWS 또는 이후 교체한 event_extended 모델을 검증한 빌드 로그는 아니다. 2026-10-08 21:01 KST에 tiny-vision-cane-6e80d의 reportFall(asia-northeast3) 서버 배포를 완료했다. 기존 DEVICE_TOKENS 버전 1을 유지했다. 보드 업로드는 수행하지 않았다.

서버 핸들러 테스트는 응답 유실 후 재전송, 동시 요청, 저장 실패 후 복구, 기기별 ID 구분, ID 충돌, 지연 이벤트의 최신 상태 보호를 검증한다. C++ 테스트는 저장 성공 전 RAM 상태 보존, 위험 우선순위, 용량 제한, 반복 실패 중 ID 유지, 삭제 실패, 저장소로부터 상태 복구를 검증한다. 테스트는 모의 Firestore/저장소를 사용하며 실제 네트워크·플래시 전원 차단·FCM 전달을 대신하지 않는다.

이번 수정의 중복 방지 대상은 Firestore 기록과 HTTP 재전송에 따른 푸시 반복이다. 서버가 이벤트를 저장한 직후 푸시를 보내기 전에 종료되면 기존 HTTP 처리 구조상 `pending` 이벤트의 푸시가 미전송될 수 있다. FCM 자체의 정확히 한 번 전달 또는 서버 종료 후 푸시 자동 복구를 보장하지 않는다. GPS도 이벤트 수신 시점의 최신 위치를 사용하므로 오프라인 동안 발생한 이벤트의 당시 위치를 복원하지는 않는다.
